One table, app.documents, holds rows for two tenants. A Rust API server and a browser WebUI sit in front of it, and PostgreSQL itself decides who may see which rows — using policies that trust nothing the client says. This page walks the entire pipeline: every function, every policy, every HTTP round-trip, and three plotted user journeys (two tenants, one attacker).

Tier 1 — Browser

The WebUI

  • Single index.html served by the same axum server (ServeDir fallback)
  • One-click demo identities: Alice (tenant A) / Bob (tenant B)
  • Ledger table + redacted bars for rows RLS hides (teacher mode)
  • Request journal showing every HTTP status, incl. 403s
Tier 2 — Rust API

rls-api (axum 0.8)

  • Two pools: app_user (real work) and superuser (teacher endpoint)
  • Every request: one transaction → app.session_verify() → query → commit
  • Holds no secret: no JWT lib, no key material, no minting
  • RLS rejections (SQLSTATE 42501) mapped to HTTP 403
Tier 3 — PostgreSQL

The enforcement point

  • Policies read app.session_claim('tenant_id') — a claim that is re-verified against the HMAC signature on every row evaluation
  • Tokens minted (app.login) and verified (app.session_verify) by SECURITY DEFINER functions; key in app.jwt_secret
  • RLS enabled and forced; owner is a NOLOGIN migration role
  • Podman container, no volume → every ./run.sh rebuilds schema from sql/00-init.sql
02

The trust boundary

mint + verify, both in the database

The core decision: the tenant id is never a session variable the client can set — it is a signed claim that PostgreSQL itself mints and re-verifies. The API cannot mint tokens (it has no secret), and a direct SQL user cannot forge one (HMAC). Two sequences make this concrete.

2.1 — Login: the database mints the token

sequenceDiagram
  actor U as User — browser
  participant API as Rust API
  participant PG as PostgreSQL
  U->>API: POST /login {email, password}
  API->>PG: SELECT * FROM app.login($1, $2)
  Note over PG: bcrypt verify — pgcrypto crypt(), cost 10
mint JWT: HMAC-SHA256, key from app.jwt_secret
  PG-->>API: token, user_id, tenant_id, display_name, expires_in
  API-->>U: 200 {token, token_type: Bearer, ...}

2.2 — Every request: the database re-verifies

sequenceDiagram
  actor U as User — browser
  participant API as Rust API
  participant PG as PostgreSQL
  U->>API: GET /documents — Authorization: Bearer <token>
  API->>PG: BEGIN
  API->>PG: SELECT * FROM app.session_verify($token)
  Note over PG: HMAC signature + expiry check
set_config('app.jwt', token, true) — transaction-local
  PG-->>API: claims — or zero rows → HTTP 401
  API->>PG: SELECT id, title, ... FROM app.documents
  Note over PG: policy: tenant_id = app.session_claim('tenant_id')::uuid
signature re-verified per row — forged GUC → NULL → deny
  PG-->>API: only this tenant's published rows
  API-->>U: 200 {count, documents}
Why the GUC is safe. app.session_verify stores the token in the session setting app.jwt. Anyone can SET that setting — but the policies never read it directly. They call app.session_claim(), which takes whatever is in the setting, recomputes the HMAC against the DB-held key, checks expiry, and only then returns the claim. A hand-written or forged value yields NULL → the row is denied. The setting is transaction-local (set_config(..., true)), so pooled connections never leak a session between requests.
app.login(email, password)

Mint — plpgsql, SECURITY DEFINER

  • Looks up app.users where password_hash = crypt($2, password_hash) — the hash never leaves the DB
  • Builds JWT: base64url(header).base64url(claims).HMAC-SHA256
  • Claims: sub, tenant_id, display_name, iat, exp (24 h)
  • Returns zero rows on bad credentials — no error, no oracle
  • search_path = pg_temp, all references qualified
app.session_verify(token)

Verify — plpgsql, SECURITY DEFINER

  • Splits on ., demands exactly 3 parts
  • Recomputes HMAC over header.payload, constant comparison with the supplied signature
  • Checks exp and required claims; zero rows if anything fails
  • On success: set_config('app.jwt', token, true) → installs the verified session
app.session_claim(name)

Policy read — STABLE, SECURITY DEFINER

  • The only function policies may trust: called per row, re-verifies the GUC's signature and expiry
  • Returns payload ->> name or NULL (never raises)
  • Policy: tenant_id = app.session_claim('tenant_id')::uuid
  • app.establish() = login + verify in one call (tests, convenience)

War story. PostgreSQL's encode(data,'base64') wraps output in newlines every 76 characters (MIME style). The first version of app.url_encode() produced tokens with embedded \n — the DB refused to decode them (invalid base64 end sequence) and HTTP headers would have rejected them too. Fix: strip \r\n before the URL-safe translate. Every layer of this system got tested into working.

Inside PostgreSQL

roles · policies · objects

Roles — ownership is for migrations, not for the app

RoleAttributesJobCan it see rows it shouldn't?
migration_runnerNOLOGIN, no BYPASSRLS Owns the app schema, all tables, policies and SECURITY DEFINER functions. Used only for DDL (init scripts, migrations). No runtime principal. no — FORCE RLS applies to it too
app_userLOGIN, password, no BYPASSRLS The API server's only login: DML on app.documents, EXECUTE on the auth functions. No ownership, no CREATE on the schema. no — RLS filters everything
rls_auditorNOLOGIN, BYPASSRLS Exists to demonstrate why BYPASSRLS is dangerous — and to own the "leaky" demo view (§5). yes — by design (demo only)
postgressuperuser Bootstrap, the SQL test suite, and the teacher-mode endpoint pool. yes — always exempt

Policies on app.documents — RLS enabled and forced

PolicyKindExpressionEffect
tenant_isolationpermissive USING + WITH CHECK:
tenant_id = app.session_claim('tenant_id')::uuid		 Row visible/insertable only if it belongs to the verified tenant. Permissive policies OR together.
published_onlyrestrictive USING (published) + WITH CHECK (published) Unpublished drafts invisible even to their own tenant, and un-insertable. Restrictive policies AND with the permissive set.
ALTER TABLE app.documents FORCE ROW LEVEL SECURITY; — policies apply to the table owner too (the migration role); without FORCE, owners bypass RLS by default (proven by owner_bypass_probe).

Object inventory

app.documents
  • 7 seeded rows: 4 tenant A (3 published, 1 draft), 3 tenant B (2 published, 1 draft)
  • RLS + FORCE; the two policies above
app.users
  • alice@alpha.example → tenant A, bob@beta.example → tenant B
  • bcrypt hashes (cost 10); no role ever SELECTs this table directly
app.jwt_secret
  • Single row, CHECK (id = 1); read only inside the SECURITY DEFINER functions
  • Demo value; rotate via migration in production
app.secret_notes
  • Leak-demonstration table: policy function RAISEs for restricted rows (§5)
app.owner_bypass_probe
  • RLS enabled but not forced + USING (false) deny policy: proves the owner-exemption default
app.v_documents_*
  • v_documents_safe: security_invoker = true
  • v_documents_leaky: owned by the BYPASSRLS auditor — the trap (§5)

Even the API can't cheat. The Rust server holds no secret and owns nothing. A compromised API can only act as app_user — and that role cannot mint tokens for tenants whose passwords it doesn't know. This is the point of moving the secret into the database: the trust anchor is the password check, not a file on the API host.
05

The closed holes

four classic RLS traps — trap vs fix
Hole 1 — the settable tenant
Classic RLS demos read current_setting('app.tenant_id') in the policy. Anyone with app_user credentials runs SET app.tenant_id = '<any tenant>' and reads everyone's rows.
Fix — verified claims
Policies call app.session_claim('tenant_id'), which re-verifies the HMAC signature of whatever sits in the session GUC. Raw SET, forged or expired tokens → NULL → default deny. Proof: test.sh §2 — set_config now returns 0 rows.
Hole 2 — the owning principal
The app role owns the tables → it can ALTER POLICY, DROP TABLE, or DISABLE ROW LEVEL SECURITY whenever it wants.
Fix — DDL-only migration role
migration_runner (NOLOGIN) owns schema, tables, policies, functions. The app role has DML + EXECUTE only, no CREATE on the schema. Proof: test.sh §11 — ALTER POLICY / DROP / CREATE all fail for app_user.
Hole 3 — leaky views
A view over an RLS table runs as its owner. If the owner is privileged, RLS is bypassed underneath and the view leaks everything to anyone with SELECT.
Fix — demonstrated both ways
app.v_documents_safe uses security_invoker = true → invoker's RLS applies (3 rows). app.v_documents_leaky, owned by the BYPASSRLS auditor, exposes all 7. Proof: test.sh §12. Rule: RLS views must be security_invoker, and privileged roles must never own queryable objects.
Hole 4 — leaking policy functions
Policies are evaluated on rows the user will never see. A function that RAISEs or branches on hidden data leaks existence through errors and timing.
Fix — demonstrated, then avoided
app.secret_notes ships a deliberately leaky policy (RAISE on restricted rows): a sessionless scan errors, proving the leak — test.sh §13. The real policies avoid functions entirely: plain column comparisons. Never LEAKPROOF, never volatile, never side-effecting.
By design, not closable: superusers and BYPASSRLS roles always bypass RLS. The countermeasure is containment — nobody at runtime holds those attributes (rls_auditor is NOLOGIN and exists only for the demo; the single superuser connection is the demo-only teacher endpoint).
